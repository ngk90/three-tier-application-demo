# Database Migrations

This application uses [node-pg-migrate](https://salsita.github.io/node-pg-migrate/) to manage database schema changes with an append-only migration pattern. Each migration is a timestamped JavaScript file that defines `up` and `down` functions to apply or roll back schema changes. Migrations are automatically applied when the application starts via Docker Compose.

## Overview

Migrations live in `src/db/migrations/` and follow a strict naming convention: `{TIMESTAMP}_{description}.js`. The timestamp ensures migrations run in order, and the append-only approach means migrations are never modified after creation—only new migrations are added to evolve the schema.

| Aspect | Details |
|--------|---------|
| **Tool** | [node-pg-migrate](https://salsita.github.io/node-pg-migrate/) v8.0.4 |
| **Location** | `src/db/migrations/` |
| **Naming** | `{TIMESTAMP}_{description}.js` (e.g., `1718500000000_initial-schema.js`) |
| **Pattern** | Append-only; never modify existing migrations |
| **Execution** | Automatic via Docker Compose `migrate` service on startup |

## Migration Structure

Each migration file exports two functions:

- **`up(pgm)`** — applies the schema change
- **`down(pgm)`** — rolls back the change (for development/testing)

The `pgm` object provides helper methods like `createTable()`, `dropTable()`, `addColumn()`, `dropColumn()`, etc.

### Example: Initial Schema

From `src/db/migrations/1718500000000_initial-schema.js`:

```javascript
exports.up = (pgm) => {
  pgm.createTable('users', {
    id: { type: 'serial', primaryKey: true },
    email: { type: 'varchar(255)', notNull: true, unique: true },
    created_at: { type: 'timestamp', notNull: true, default: pgm.func('now()') },
  });
};

exports.down = (pgm) => {
  pgm.dropTable('users');
};
```

### Example: Adding a Table

From `src/db/migrations/1718500001000_create-tasks.js`:

## Running Migrations

### Automatic (Docker Compose)

When you run `docker compose up`, the `migrate` service automatically applies all pending migrations before the API starts:

```bash
docker compose up --build
```

The `migrate` service:
1. Waits for PostgreSQL to be healthy
2. Runs `npx node-pg-migrate up`
3. Exits after migrations complete
4. The API then starts with the updated schema

### Manual (Local Development)

To run migrations manually, set the `DATABASE_URL` environment variable and use npm scripts from `src/db/`:

```bash
cd src/db

# Apply all pending migrations
DATABASE_URL=postgres://app:app@localhost:5432/app npm run migrate

# Roll back the last migration
DATABASE_URL=postgres://app:app@localhost:5432/app npm run migrate:down
```

The `DATABASE_URL` format is `postgres://[user]:[password]@[host]:[port]/[database]`.

## Creating a New Migration

To add a new migration:

1. **Generate a timestamped file** in `src/db/migrations/`:
   ```bash
   touch src/db/migrations/$(date +%s)000_your_description.js
   ```

2. **Write the `up` function** with your schema changes:
   ```javascript
   exports.up = (pgm) => {
     pgm.addColumn('tasks', 'priority', {
       type: 'integer',
       notNull: true,
       default: 0,
     });
   };
   ```

3. **Write the `down` function** to reverse the change:
   ```javascript
   exports.down = (pgm) => {
     pgm.dropColumn('tasks', 'priority');
   };
   ```

4. **Test locally**:
   ```bash
   docker compose up --build
   ```

## Best Practices

- **Never modify existing migrations** — always create a new migration for schema changes
- **Test both `up` and `down`** — ensure rollbacks work correctly
- **Use descriptive names** — e.g., `1718500002000_add-priority-to-tasks.js`
- **Keep migrations focused** — one logical change per migration
- **Use timestamps** — ensures deterministic ordering across environments
- **Document complex changes** — add comments explaining why a change was made
