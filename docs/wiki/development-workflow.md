# Development Workflow

This page covers best practices for developing features across the three tiers of the application and working effectively with AI agents to accelerate development.

## Local Development Setup

Start the full stack with Docker Compose:

```bash
docker compose up --build
```

This orchestrates four services in dependency order:

1. **postgres** — PostgreSQL 17 database (waits until healthy)
2. **migrate** — applies schema migrations, then exits
3. **api** — Express API on port 3001 (internal only)
4. **web** — Next.js frontend on port 3000 (exposed to `http://localhost:3000`)

After changes to any tier, rebuild with `docker compose up --build`. To reset data, run `docker compose down -v`.

## Feature Development Workflow

The three-tier architecture creates natural seams for incremental development. Follow this order to minimize debugging:

### 1. Database Layer First

Start with the schema. Create a new migration in `src/db/migrations/`:

```bash
cd src/db
DATABASE_URL=postgres://app:app@localhost:5432/app npx node-pg-migrate create add-priority-column
```

Edit the migration file to define your schema change. Migrations are **append-only** — never edit an existing migration; create a new one if you need to fix something.

Apply it locally:

```bash
docker compose up migrate
```

Verify the schema with a database client or by inspecting the logs.

### 2. API Layer Second

Add endpoints in `src/api/index.js` to expose the new data. Test with curl before wiring the frontend:

```bash
# Map the API port temporarily to test
docker compose exec api curl http://localhost:3001/tasks
```

Verify error handling and status codes. Check for N+1 queries and connection pool issues.

### 3. Frontend Layer Last

Wire up the UI in `src/web/app/page.tsx` or `src/web/app/actions.ts`. Use the API URL from the environment variable `API_URL` (set to `http://api:3001` in Docker Compose).

This order prevents cascading failures: if the schema is wrong, you catch it before writing API logic; if the API is broken, you catch it before building UI.

## Working with AI Agents

The repository includes `agents.md` with detailed guidance for using Claude Code and other AI tools. Key principles:

### Scope Changes to One Tier

Ask the AI agent to work on one layer at a time:

> "Add a `priority` column to the tasks table. Create the migration, update the API to accept and return it, and show it in the UI."

Instead, break it into three requests:

1. "Create a node-pg-migrate migration that adds a `priority` column (integer, default 0) to the tasks table."
2. "Update the API to accept and return the priority field in GET /tasks and POST /tasks."
3. "Update the frontend to display and edit the priority field."

### Give Context, Not Just Commands

Instead of:
> "Fix the bug"

Try:
> "The PATCH /tasks/:id endpoint returns 200 even when the id doesn't exist. Fix it to return 404."

### Let the Agent Run the App

AI agents can execute `docker compose up` and observe logs. Ask:

> "Run docker compose up and tell me what errors appear in the logs."

This is faster than describing symptoms.

### Use Agents for One-Off Tasks

Generate scripts for seeding data or inspecting state:

> "Write a script that seeds the tasks table with 10 sample tasks using the API's POST /tasks endpoint."

## Project Conventions

| Convention | Details |
|-----------|---------|
| **Migrations** | Append-only; never edit existing files. Create a new migration to fix mistakes. |
| **API visibility** | The API is internal to the Docker network. All external traffic goes through the web tier. |
| **Configuration** | Use environment variables for connection strings, ports, and URLs. No hardcoded values. |
| **Versions** | Node 22 and PostgreSQL 17. Match these in any new Dockerfiles or dependencies. |

## Testing the API

The API includes unit tests in `src/api/index.test.js`. Run them inside the container:

```bash
docker compose exec api npm test
```

When adding endpoints, write tests alongside the implementation. This catches integration issues early.

## Debugging Tips

- **Check service health**: `docker compose ps` shows which services are running and their status.
- **Read logs**: `docker compose logs <service>` shows output from any tier. Use `--follow` to stream.
- **Inspect the database**: Connect with `docker compose exec postgres psql -U app -d app` and run SQL directly.
- **Verify environment variables**: Each service reads its config from `docker-compose.yml`. Check that `DATABASE_URL`, `API_URL`, and `PORT` are set correctly.
- **Rebuild cleanly**: If a service won't start, try `docker compose down -v && docker compose up --build`.

## Deployment Workflow

Before deploying to GCP, ensure:

1. All migrations are tested locally and committed.
2. The API passes all tests: `docker compose exec api npm test`.
3. The frontend builds without errors: `docker compose exec web npm run build`.
4. Environment variables are documented in `.env.example`.

See the "Deployment to GCP" page for Terraform and Cloud Run setup.
