# Development Workflow

This page guides you through adding features across the three tiers and working effectively with AI agents on this codebase. The application follows a clear separation of concerns: the frontend (`src/web/`) communicates with the API (`src/api/`), which queries the database (`src/db/`). Understanding this flow is essential for productive development.

## Adding Features Across the Three Tiers

When adding a new feature, work from the database layer upward. This ensures your schema is correct before building the API and UI on top of it.

### 1. Database Layer: Create a Migration

Start by defining the schema change in `src/db/migrations/`. Use [node-pg-migrate](https://salsita.github.io/node-pg-migrate/) to create a new migration file:

```bash
cd src/db
npx node-pg-migrate create add-priority-column
```

This generates a timestamped file in `src/db/migrations/`. Edit it to define your schema change:

```javascript
// Example: add a priority column to tasks
exports.up = (pgm) => {
  pgm.addColumn('tasks', {
    priority: { type: 'integer', default: 0 },
  });
};

exports.down = (pgm) => {
  pgm.dropColumn('tasks', 'priority');
};
```

**Key rule:** Migrations are append-only. Never edit an existing migration file; create a new one instead.

### 2. API Layer: Add the Endpoint

Update `src/api/index.js` to handle the new field. For example, if you added a `priority` column:

```javascript
// PATCH /tasks/:id — update priority
app.patch('/tasks/:id', async (req, res) => {
  const id = parseInt(req.params.id, 10);
  const { completed, title, priority } = req.body;
  // ... fetch current task, merge fields, update database
});
```

Test the endpoint locally before moving to the frontend:

```bash
docker compose up
# In another terminal:
curl -X PATCH http://localhost:3001/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"priority": 2}'
```

### 3. Frontend Layer: Wire Up the UI

Update `src/web/app/actions.ts` to send the new field to the API, and update `src/web/app/page.tsx` to display and allow editing it. The frontend uses Next.js Server Actions to communicate with the API:

```typescript
// src/web/app/actions.ts
export async function updateTaskPriority(id: number, priority: number) {
  await fetch(`${API_URL}/tasks/${id}`, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ priority }),
  });
  revalidatePath('/');
}
```

## Local Development with Docker Compose

### Starting the Stack

```bash
docker compose up --build
```

This starts four services in order:

| Service | Purpose | Port |
|---------|---------|------|
| **postgres** | PostgreSQL 17 database | 5432 (internal) |
| **migrate** | Runs migrations, then exits | — |
| **api** | Express REST API | 3001 (internal) |
| **web** | Next.js frontend | 3000 (exposed) |

The API is not exposed to your host machine; all external traffic flows through the web tier. This enforces the three-tier architecture.

### Rebuilding After Changes

```bash
# Rebuild and restart all services
docker compose up --build

# Rebuild only the API
docker compose up --build api

# Stop all services (keeps database volume)
docker compose down

# Stop and delete all data
docker compose down -v
```

### Debugging

View logs from a specific service:

```bash
docker compose logs -f api
docker compose logs -f web
docker compose logs -f postgres
```

## Working with AI Agents

Claude Code and similar AI agents can accelerate development on this codebase. Use these patterns for best results.

### Scoped Prompts Work Best

Instead of broad requests, give Claude specific context:

**Good:**
> "Add a DELETE /tasks/:id endpoint to the API that returns 404 if the task doesn't exist, then wire it up to a delete button in the frontend."

**Less effective:**
> "Add delete functionality"

### One Layer at a Time

Break feature work into database → API → frontend steps. Ask Claude to complete one layer, then verify it works before moving to the next:

```
1. Create a migration that adds a due_date column to tasks.
2. Add a PATCH endpoint that accepts and returns due_date.
3. Update the frontend to show and edit due dates.
```

### Suggested Prompts

**Understanding the codebase:**
- "Explain how a task flows from the browser through the web tier, to the API, and into the database."
- "What tables exist in the database and what are their schemas?"
- "Walk me through what happens when `docker compose up` runs, in order."

**Adding features:**
- "Add a DELETE /tasks/:id endpoint to the API and wire it up to a delete button in the frontend."
- "Add a due_date column to the tasks table. Create the migration, update the API to accept and return it, and show it in the UI."
- "Add input validation to the POST /tasks endpoint so that titles longer than 200 characters are rejected with a 422 status."

**Database work:**
- "Create a node-pg-migrate migration that adds a priority column (integer, default 0) to the tasks table."
- "Show me all the migrations that have been applied and what schema they created."

**Docker and infrastructure:**
- "The migrate service keeps restarting. Read the Dockerfile and docker-compose.yml and tell me why."
- "Explain the Terraform in src/infrastructure/ and what GCP resources it creates."

**Code review:**
- "Review the API's error handling. Are there cases where the server could crash or return an unhelpful error?"
- "Is there any N+1 query risk in the API? Check all database calls."

### Tips for AI-Assisted Development

- **Let Claude run the app** — Ask it to execute `docker compose up` and observe logs. If something breaks, ask what errors appear.
- **Ask for explanations first** — Before a risky change (schema migration, refactor), ask Claude to explain its plan.
- **Use it for one-off scripts** — "Write a script that seeds the tasks table with 10 sample tasks using the API's POST /tasks endpoint."
- **Give context, not just commands** — Tell Claude which endpoint is broken and what the expected behavior is, so it can find the relevant file faster.

## Project Conventions

- **Migrations are append-only** — Never edit an existing migration; create a new one.
- **The API is internal** — It's not exposed outside the Docker network. All external traffic goes through the web tier.
- **Environment variables are the config boundary** — Connection strings, ports, and URLs are passed via env vars. No hardcoded values.
- **Node 22 / PostgreSQL 17** — Match these versions in any new Dockerfiles or dependencies.

## Testing

### Unit Tests

The API includes a test file at `src/api/index.test.js`. Run tests locally:

```bash
cd src/api
npm test
```

### Manual Testing

Test API endpoints directly using curl or a tool like Postman. The web tier calls the API via Server Actions in `src/web/app/actions.ts`, so you can also test by interacting with the UI at http://localhost:3000.
