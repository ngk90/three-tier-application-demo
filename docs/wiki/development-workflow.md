# Development Workflow

This guide covers best practices for adding features across the three tiers of this application and working effectively with AI agents on this codebase. The three-tier architecture (frontend → API → database) creates natural seams where you can scope work incrementally, test each layer independently, and collaborate with AI tools to accelerate development.

## Local Development Setup

Start the entire stack with Docker Compose:

```bash
docker compose up --build
```

This starts four services in dependency order:

1. **postgres** — PostgreSQL 17 database (waits until healthy)
2. **migrate** — applies schema migrations, then exits
3. **api** — Express API on port 3001 (internal only)
4. **web** — Next.js frontend on port 3000 (exposed to host)

Once running, open [http://localhost:3000](http://localhost:3000).

### Rebuilding after code changes

```bash
# Rebuild and restart all services
docker compose up --build

# Stop containers (keeps postgres_data volume)
docker compose down

# Stop and delete all data
docker compose down -v
```

The `docker-compose.yml` defines service dependencies: the web tier waits for the API, the API waits for migrations, and migrations wait for the database to be healthy. If a service fails to start, check the logs with `docker compose logs <service>`.

## Adding Features: Layer-by-Layer Approach

Three-tier applications have natural seams at each layer boundary. When adding a feature, work through the layers in order and verify each before moving on. This approach reduces debugging complexity and makes it easier to pinpoint where issues occur.

### 1. Database layer: Create a migration

Migrations live in `src/db/migrations/` and use [node-pg-migrate](https://salsita.github.io/node-pg-migrate/). Always create a new migration file; never edit an existing one.

**Example:** Add a `due_date` column to the tasks table.

```bash
cd src/db
npx node-pg-migrate create add-due-date-to-tasks
```

This creates a timestamped file like `1234567890_add-due-date-to-tasks.js`. Edit it to define the schema change:

```javascript
exports.up = (pgm) => {
  pgm.addColumn('tasks', {
    due_date: { type: 'timestamp', notNull: false },
  });
};

exports.down = (pgm) => {
  pgm.dropColumn('tasks', 'due_date');
};
```

When you run `docker compose up`, the `migrate` service automatically applies all pending migrations. If a migration fails, the API will not start (by design).

### 2. API layer: Add the endpoint

The API lives in `src/api/` and uses Express 5. Add a route handler that reads from or writes to the database.

**Example:** Update the PATCH `/tasks/:id` endpoint to accept and persist `due_date`:

```javascript
// src/api/index.js
app.patch('/tasks/:id', async (req, res) => {
  const { id } = req.params;
  const { title, completed, due_date } = req.body;
  
  const result = await db.query(
    'UPDATE tasks SET title = COALESCE($1, title), completed = COALESCE($2, completed), due_date = COALESCE($3, due_date) WHERE id = $4 RETURNING *',
    [title, completed, due_date, id]
  );
  
  if (result.rows.length === 0) {
    return res.status(404).json({ error: 'Task not found' });
  }
  
  res.json(result.rows[0]);
});
```

Test the endpoint with curl or a tool like Postman. The API is not exposed outside the Docker network, but you can temporarily map its port:

```bash
docker compose up --build -p 3001:3001
curl -X PATCH http://localhost:3001/tasks/1 -H "Content-Type: application/json" -d '{"due_date":"2025-12-31T23:59:59Z"}'
```

### 3. Frontend layer: Wire up the UI

The frontend lives in `src/web/` and uses Next.js 16 with React 19. Add a form field or display element that calls the API endpoint.

**Example:** Add a due date input to the task form:

```javascript
// src/web/app/page.js
const [dueDate, setDueDate] = useState('');

const handleUpdate = async (id) => {
  await fetch('/api/tasks/' + id, {
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ due_date: dueDate }),
  });
};
```

The frontend communicates with the API via the `API_URL` environment variable (set to `http://api:3001` in `docker-compose.yml`). Next.js API routes in `src/web/app/api/` act as a proxy to avoid CORS issues.

## Working with AI Agents

The `agents.md` file contains detailed guidance on using Claude Code with this codebase. Here are the key patterns:

### Scope tasks to one tier at a time

Instead of asking an AI agent to "add a feature," be specific about which tier:

- ❌ "Add a priority field to tasks"
- ✅ "Create a node-pg-migrate migration that adds a priority column (integer, default 0) to the tasks table"
- ✅ "Add a PATCH endpoint that updates the priority field and returns the updated task"
- ✅ "Add a priority dropdown to the task form in the UI"

### Give context, not just commands

Include the expected behavior and any constraints:

- ❌ "Fix the bug"
- ✅ "The PATCH /tasks/:id endpoint returns 200 even when the id doesn't exist. Fix it to return 404 instead."

### Let the agent run the app

Claude Code can execute `docker compose up` and observe logs. If something breaks at runtime:

```
Run docker compose up and tell me what errors appear in the logs.
```

### Ask for explanations before risky changes

Before a schema migration or refactor, ask the agent to explain its plan first:

```
Before you make any changes, explain your plan for adding user authentication to this app.
```

### Use agents for one-off scripts

For tasks like seeding data or inspecting the database:

```
Write a script that seeds the tasks table with 10 sample tasks using the API's POST /tasks endpoint.
```

## Project Conventions

These conventions ensure consistency and prevent common mistakes:

| Convention | Reason |
|-----------|--------|
| **Migrations are append-only** | Rolling back a migration in production is risky; create a new migration to undo changes. |
| **The API is internal** | It's not exposed outside the Docker network; all external traffic goes through the web tier. |
| **Environment variables are the config boundary** | Connection strings, ports, and URLs are all passed via env vars. No hardcoded values. |
| **Node 22 / PostgreSQL 17** | Match these versions in any new Dockerfiles or dependencies. |

## Debugging Common Issues

### The migrate service keeps restarting

Check the migration logs:

```bash
docker compose logs migrate
```

Common causes:
- **Syntax error in migration file** — node-pg-migrate will report the line number.
- **Database not ready** — the postgres service healthcheck may be failing; check `docker compose logs postgres`.
- **Migration already applied** — if you edited an existing migration file, the database still has the old version. Roll back with `docker compose down -v` to delete the database and start fresh.

### The API returns 500 errors

Check the API logs:

```bash
docker compose logs api
```

Common causes:
- **Database connection failed** — verify the `DATABASE_URL` environment variable matches the postgres credentials.
- **Query syntax error** — check the SQL in your endpoint handler.
- **Missing column** — if you added a new column but didn't run migrations, the query will fail.

### The frontend can't reach the API

The frontend uses the `API_URL` environment variable (set to `http://api:3001` in `docker-compose.yml`). If you're running the frontend outside Docker, change it to `http://localhost:3001`.

## Testing Workflow

### Unit testing the API

Create a test file in `src/api/` and use a testing framework like Jest or Vitest:

```javascript
// src/api/index.test.js
import request from 'supertest';
import app from './index.js';

describe('GET /tasks', () => {
  it('returns an array of tasks', async () => {
    const res = await request(app).get('/tasks');
    expect(res.status).toBe(200);
    expect(Array.isArray(res.body)).toBe(true);
  });
});
```

Run tests inside the api container:

```bash
docker compose exec api npm test
```

### Integration testing with curl

Test the full stack by making HTTP requests to the API:

```bash
# Create a task
curl -X POST http://localhost:3001/tasks \
  -H "Content-Type: application/json" \
  -d '{"title":"Buy milk"}'

# List tasks
curl http://localhost:3001/tasks

# Update a task
curl -X PATCH http://localhost:3001/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"completed":true}'
```

### Manual testing in the browser

Open [http://localhost:3000](http://localhost:3000) and use the UI. Open the browser DevTools (F12) to see network requests and console errors.

## Code Review Checklist

Before committing changes, verify:

- [ ] **Migrations are idempotent** — running the same migration twice should not fail.
- [ ] **API endpoints validate input** — reject invalid data with a 422 status, not a 500.
- [ ] **Error messages are helpful** — include the reason for the error, not just "error".
- [ ] **The frontend handles loading and error states** — don't leave the user hanging.
- [ ] **Environment variables are documented** — add them to `.env.example` if they're new.
- [ ] **Docker Compose still works** — run `docker compose up --build` and verify all services start.
