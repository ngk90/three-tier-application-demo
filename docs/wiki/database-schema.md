# Database Schema & Migrations

_Generated by Forge from `main` at `9e9f20c`._

The application uses PostgreSQL 17 with schema changes managed through [node-pg-migrate](https://salsita.github.io/node-pg-migrate/), a lightweight migration tool for Node.js. Migration files are version-controlled in `src/db/migrations/` and applied automatically when the application starts via Docker Compose or during deployment to GCP.

## Schema Overview

The database currently contains two tables supporting a simple task manager application:

| Table | Purpose |
|-------|---------|
| `users` | Stores user accounts (currently unused in the demo) |
| `tasks` | Stores task items with completion status |

### Users Table

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  email VARCHAR(255) NOT NULL UNIQUE,
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
```

The `users` table is created by the initial migration but not yet integrated into the API. It provides a foundation for future multi-user features.

### Tasks Table

```sql
CREATE TABLE tasks (
  id SERIAL PRIMARY KEY,
  title VARCHAR(500) NOT NULL,
  completed BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMP NOT NULL DEFAULT now()
);
```

The `tasks` table stores individual task items. The `completed` field tracks whether a task is done, and `created_at` records when the task was added.

## Migration Files

Migrations are stored in `src/db/migrations/` with filenames following the pattern `{timestamp}_{description}.js`. Each file exports `up` and `down` functions:

- **`1718500000000_initial-schema.js`** — Creates the `users` table

### Migration Structure

Each migration file uses the node-pg-migrate API:

```javascript
exports.up = (pgm) => {
  // Apply changes
  pgm.createTable('tasks', { ... });
};

exports.down = (pgm) => {
  // Rollback changes
  pgm.dropTable('tasks');
};
```

## Running Migrations

### Automatic (Docker Compose)

When you run `docker compose up`, the `migrate` service automatically applies all pending migrations before the API starts:

```bash
docker compose up --build
```

The `migrate` service runs once and exits after migrations complete.

### Manual

To run migrations manually, set the `DATABASE_URL` environment variable and use npm scripts in `src/db/`:

```bash
cd src/db
DATABASE_URL=postgres://app:app@localhost:5432/app npm run migrate
```

To roll back the last migration:

```bash
DATABASE_URL=postgres://app:app@localhost:5432/app npm run migrate:down
```

## Migration Execution

The migration process is containerized in `src/db/Dockerfile`:

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY migrations ./migrations
CMD ["npx", "node-pg-migrate", "up"]
```

This image:
1. Installs dependencies (node-pg-migrate and pg driver)
2. Copies migration files
3. Runs `node-pg-migrate up` to apply pending migrations

The container connects to the PostgreSQL instance via the `DATABASE_URL` environment variable, which is set in `docker-compose.yml` or Terraform configuration.

## Adding New Migrations

To create a new migration:

1. Generate a new file with a unique timestamp prefix:
   ```bash
   cd src/db
   npx node-pg-migrate create "add-user-id-to-tasks"
   ```

2. Edit the generated file in `migrations/` to define your schema changes in the `up` function and rollback logic in the `down` function.

3. Commit the migration file to version control.

4. On next deployment or `docker compose up`, the migration runs automatically.

## Database Connection

The API connects to PostgreSQL via `src/api/db.js` using the `pg` package. The connection pool reads the `DATABASE_URL` environment variable, which is set by Docker Compose or Terraform depending on the deployment environment.
