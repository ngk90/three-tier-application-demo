# Project Structure

This three-tier application is organized into four main directories under `src/`, each with its own Dockerfile and dependencies. The frontend, API, database migrations, and infrastructure code are separated to allow independent development, testing, and deployment of each tier.

## Directory Layout

```
src/
├── api/            # Express REST API (Node.js)
├── db/             # Database migrations (node-pg-migrate)
├── web/            # Next.js frontend (React)
└── infrastructure/ # Terraform configuration (GCP)
```

## Frontend (`src/web/`)

The frontend is a **Next.js 16** application with React 19 and Tailwind CSS, providing a modern single-page interface for the task manager.

| File/Folder | Purpose |
|-------------|---------|
| `app/` | Next.js App Router pages and components |
| `app/page.tsx` | Main task manager UI |
| `app/actions.ts` | Server actions for API communication |
| `app/layout.tsx` | Root layout and metadata |
| `app/globals.css` | Global styles and Tailwind imports |
| `public/` | Static assets (icons, images) |
| `package.json` | Dependencies: Next.js, React, Tailwind CSS |
| `Dockerfile` | Multi-stage build for production |
| `next.config.ts` | Next.js configuration |
| `tsconfig.json` | TypeScript configuration |

The frontend runs on port 3000 and communicates with the API via the `API_URL` environment variable (set to `http://api:3001` in Docker Compose).

## API (`src/api/`)

The API is an **Express 5** REST service written in Node.js 22, handling all business logic and database queries.

| File | Purpose |
|------|---------|
| `index.js` | Route handlers and Express server setup |
| `db.js` | PostgreSQL connection pool configuration |
| `index.test.js` | Jest tests for API endpoints |
| `package.json` | Dependencies: Express, pg (PostgreSQL driver) |
| `Dockerfile` | Container image for the API service |

The API exposes endpoints at `/health`, `/tasks`, and `/tasks/:id` (see "API Endpoints" page for details). It connects to PostgreSQL using the `DATABASE_URL` environment variable.

## Database (`src/db/`)

Database schema and migrations are managed with **node-pg-migrate**, allowing version-controlled schema changes.

| File/Folder | Purpose |
|-------------|---------|
| `migrations/` | Migration files (numbered by timestamp) |
| `migrations/1718500000000_initial-schema.js` | Creates initial schema (extensions, roles) |
| `migrations/1718500001000_create-tasks.js` | Creates the `tasks` table |
| `package.json` | Dependencies: node-pg-migrate, pg |
| `Dockerfile` | Runs migrations on startup |

Migrations are applied automatically when the Docker Compose stack starts (via the `migrate` service). See "Database Schema & Migrations" for details on running migrations manually.

## Infrastructure (`src/infrastructure/`)

Terraform configuration for deploying the application to Google Cloud Platform, provisioning all necessary resources.

| File | Purpose |
|------|---------|
| `main.tf` | Primary resource definitions (VPC, Cloud SQL, Cloud Run) |
| `variables.tf` | Input variables (project ID, image URIs, region) |
| `outputs.tf` | Output values (web URL, API URL) |
| `migration.tf` | Cloud Run job for running database migrations |
| `terraform.tfvars.example` | Example variable values (copy and customize) |

The infrastructure creates a private VPC, a managed PostgreSQL instance on Cloud SQL, and Cloud Run services for both the API and frontend. See "Deployment to GCP" for deployment instructions.

## Docker Compose Orchestration

The `docker-compose.yml` file at the repository root defines the local development stack with four services:

```yaml
postgres  → migrate → api → web
```

| Service | Image | Port | Purpose |
|---------|-------|------|---------|
| `postgres` | `postgres:17-alpine` | 5432 (internal) | PostgreSQL database |
| `migrate` | Built from `src/db/Dockerfile` | — | Runs migrations, then exits |
| `api` | Built from `src/api/Dockerfile` | 3001 (internal) | Express REST API |
| `web` | Built from `src/web/Dockerfile` | 3000 (exposed) | Next.js frontend |

Services depend on each other: `migrate` waits for `postgres` to be healthy, `api` waits for `migrate` to complete, and `web` waits for `api` to be ready. The `postgres_data` volume persists the database across container restarts.

## Development Workflow

1. **Frontend changes**: Edit files in `src/web/app/` and the dev server hot-reloads
2. **API changes**: Edit `src/api/index.js` or `src/api/db.js` and restart the container
3. **Database schema changes**: Create a new migration in `src/db/migrations/` and run `docker compose up --build`
4. **Infrastructure changes**: Edit Terraform files in `src/infrastructure/` and run `terraform apply`

Run `docker compose up --build` to rebuild all images after code changes.
